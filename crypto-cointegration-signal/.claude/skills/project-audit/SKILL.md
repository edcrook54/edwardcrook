# Project Audit

## Overview

This is the orchestrator for the project's four domain checkers
(`lopez-de-prado-checker`, `probability-test-checker`,
`chart-sense-checker`, `narrative-checker`). It exists because a single
reviewer - especially the same agent that built the thing - tends to
re-confirm its own choices rather than find what's actually wrong with
them. Four independently-briefed reviewers, each with a narrow lens and
none of them carrying the builder's assumptions, catch more than one
generalist pass does; and when two of them converge on the same root
cause from different angles (e.g. the financial-ML checker flags
selection bias via PBO while the narrative checker flags the same gap as
an undisclosed "best of N" claim), that convergence is itself a stronger
signal than either finding alone.

This mirrors (and is directly modeled on) the `dispatching-parallel-agents`
and `requesting-code-review` patterns: give each reviewer precisely the
context it needs for its lens, never your own session history, run them
in parallel, and only synthesize after all four have reported back
independently.

## When to Use

Once the project's code, notebooks, and README are in a state you'd
otherwise call "done" - this is the gate before that call, not a
mid-development sanity check. Re-run it after any change material enough
to move a headline number or add a new chart.

## Process

### 1. Confirm the project is actually ready to audit

Don't dispatch reviewers against a moving target. Confirm: tests pass,
notebooks execute cleanly end to end, and the README's numbers were
generated by the most recent run (if unsure, re-run the pipeline first).

### 2. Dispatch all four checkers in parallel, each scoped narrowly

For each of the four skills, write a self-contained brief - not a copy
of your own context - that gives that reviewer exactly what it needs:

- The skill name to use (so it loads that SKILL.md's checklist).
- The specific file paths relevant to its lens (e.g. the chart checker
  gets a list of every PNG in `outputs/figures/` plus the notebooks that
  generated them; the narrative checker gets the README and CLAUDE.md
  paths plus the `outputs/tables/*.csv` files to check numbers against).
- Nothing about what the other three checkers are doing, and nothing
  about what you already suspect is wrong - a reviewer primed with the
  builder's suspicions just confirms them.

Issue all four dispatches in the same turn so they run concurrently, not
sequentially.

### 3. Collect findings independently

Each checker reports back its own Critical/Important/Minor list per its
skill's Output Format section, including explicit passes. Do not let one
checker's report influence how you read another's before all four are
in.

### 4. Synthesize

Once all four have reported:

- **Cross-reference before deduplicating.** If two checkers flag related
  issues from different angles (this will happen - it's a designed
  feature, not noise, see Overview), present them as one *elevated*
  finding that names both angles, rather than picking one checker's
  phrasing and dropping the other's.
- **Re-rank by combined severity**, not just each checker's own tier - a
  finding independently raised as "Important" by two different lenses
  should usually be read as effectively Critical.
- **Keep every checker's explicit passes in the synthesis**, not just
  the failures - a synthesis that only lists problems misrepresents how
  much of the project each reviewer actually checked and approved.
- **Write the output as a standalone report** (e.g. `AUDIT.md` at the
  project root): one section per severity tier, each finding with its
  source checker(s), file/line, and a concrete suggested fix. This is a
  project artifact in its own right, not a transient chat summary - it
  should be legible to someone who wasn't in the room in for the audit.

### 5. Act on it deliberately, don't auto-apply everything

Fix what's cheap and clearly correct. For anything that would change a
reported headline number or require redesigning a component, surface it
as a recommendation and let the project owner decide - the point of this
gate is informed decision-making, not autopilot remediation.

## Quick Reference

| Step | Who does it | Output |
|---|---|---|
| 1. Readiness check | You | Confirmed tests pass, notebooks fresh |
| 2. Dispatch | You, in parallel | 4 scoped subagent briefs, one per skill |
| 3. Collect | 4 independent subagents | 4 Critical/Important/Minor reports |
| 4. Synthesize | You | `AUDIT.md`, cross-referenced and re-ranked |
| 5. Act | You + project owner | Cheap fixes applied; rest left as recommendations |

## Red Flags

- Dispatching the four checkers sequentially instead of in parallel
  (wastes the independence - later checkers can be contaminated by
  having your running commentary on earlier ones in context).
- Writing each checker's brief by pasting your own session history
  instead of a clean, scoped brief - this hands them your framing along
  with the facts.
- Silently dropping a finding during synthesis because it's
  inconvenient, rather than either fixing it or recording it as a
  deliberate deferral.
- Treating the synthesis as a checklist to clear rather than a decision
  document - not every finding needs a code change; it needs an honest
  disposition (fixed, deferred with reason, or disagreed with and why).

## Rationalization Table

| Excuse | Reality |
|---|---|
| "I already know what these will find, I built it" | That's exactly the bias this process exists to route around - builder-confirmed findings and independently-discovered findings are not the same evidence, even when the conclusion matches. |
| "Running four subagents is overkill for one project" | The cost is one parallel dispatch, not four sequential sessions - and a finding caught here is far cheaper than one caught by an interviewer or a live trading loss. |
| "Two checkers found basically the same thing, that's redundant" | Convergent findings from independent lenses are the strongest signal this process produces - report them together, don't discard the weaker-looking duplicate. |

## Output Format

`AUDIT.md`, structured as: one paragraph on what was audited and when,
then Critical / Important / Minor sections (each finding tagged with its
source checker(s), file/line, and suggested fix), then a closing
"Verified sound" list pulled from every checker's explicit passes.
