# Project Audit

## Overview

This is the orchestrator for this project's four domain checkers
(`retrieval-validity-checker`, `production-robustness-checker`,
`citation-provenance-checker`, `narrative-checker`). It exists because a
single reviewer, especially the same agent that built the thing, tends to
re-confirm its own choices instead of finding what's actually wrong with
them. Four independently-briefed reviewers, each with a narrow lens and
none of them carrying the builder's assumptions, catch more than one
generalist pass does; and when two of them converge on the same root cause
from different angles, that convergence is itself a stronger signal than
either finding alone.

This mirrors (and is directly modeled on) `crypto-cointegration-signal`'s
`project-audit` skill: give each reviewer precisely the context it needs
for its lens, never your own session history, run them in parallel, and
only synthesize after all four have reported back independently.

## When to Use

Once the project's code, eval harness, and README are in a state you'd
otherwise call "done." This is the gate before that call, not a
mid-development sanity check. Re-run it after any change material enough to
move the headline Recall@10 table or add a new eval tier.

## Process

### 1. Confirm the project is actually ready to audit

Confirm: `make lint && make typecheck && make test` all pass, `make index`
and `make eval` run cleanly end to end, and the README's headline table was
generated by the most recent `make eval` run (if unsure, re-run it first).

### 2. Dispatch all four checkers in parallel, each scoped narrowly

For each of the four skills, write a self-contained brief, not a copy of
your own context, that gives that reviewer exactly what it needs:

- The skill name to use (so it loads that SKILL.md's checklist).
- The specific file paths relevant to its lens (e.g. the citation checker
  gets `src/tradingrag/ingest/chunk.py` and a sample of real `/search`
  responses; the narrative checker gets `README.md`, `CLAUDE.md`, and the
  `config/eval/*.json` files to check numbers against).
- Nothing about what the other three checkers are doing, and nothing about
  what you already suspect is wrong.

Issue all four dispatches in the same turn so they run concurrently, not
sequentially.

### 3. Collect findings independently

Each checker reports back its own Critical/Important/Minor list per its
skill's Output Format section, including explicit passes. Do not let one
checker's report influence how you read another's before all four are in.

### 4. Synthesize

- **Cross-reference before deduplicating.** Related issues from different
  angles should be presented as one *elevated* finding naming both angles.
- **Re-rank by combined severity**, not just each checker's own tier.
- **Keep every checker's explicit passes in the synthesis.**
- **Write the output as a standalone report** (`AUDIT.md` at the project
  root): one section per severity tier, each finding with its source
  checker(s), file/line, and a concrete suggested fix.

### 5. Act on it deliberately, don't auto-apply everything

Fix what's cheap and clearly correct. For anything that would change a
reported headline number or require redesigning a component, surface it as
a recommendation and let the project owner decide.

## Quick Reference

| Step | Who does it | Output |
|---|---|---|
| 1. Readiness check | You | Confirmed tests pass, eval fresh |
| 2. Dispatch | You, in parallel | 4 scoped subagent briefs, one per skill |
| 3. Collect | 4 independent subagents | 4 Critical/Important/Minor reports |
| 4. Synthesize | You | `AUDIT.md`, cross-referenced and re-ranked |
| 5. Act | You + project owner | Cheap fixes applied; rest left as recommendations |

## Red Flags

- Dispatching the four checkers sequentially instead of in parallel.
- Writing each checker's brief by pasting your own session history instead
  of a clean, scoped brief.
- Dropping a finding during synthesis without a note, just because it's inconvenient.
- Treating the synthesis as a checklist to clear rather than a decision
  document.

## Output Format

`AUDIT.md`, structured as: one paragraph on what was audited and when, then
Critical / Important / Minor sections (each finding tagged with its source
checker(s), file/line, and suggested fix), then a closing "Verified sound"
list pulled from every checker's explicit passes.
